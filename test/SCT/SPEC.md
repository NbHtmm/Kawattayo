# かわったよ Avalonia版：SCT試験仕様

SCTは、**利用者が配布版で目的を達成できるか**を確かめる。実装の関数名ではなく、利用者の目的・前提・操作・外から確認できる結果を記録する。対象は配布ZIPを展開した実行ファイル。既存の単体・結合テストに通っても、ここでの合格にはならない。

## ケース一覧

| ID | 利用者がしたいこと | 実施方法 |
|---|---|---|
| [SCT-CLI-001](#sct-cli-001) | 試験前を基準に、変わったログだけを別フォルダに保存する | 自動 |
| [SCT-GUI-001](#sct-gui-001) | ランチャー等から差分収集画面を直接開く | 自動 |
| [SCT-GUI-002](#sct-gui-002) | 共有フォルダを開かずに更新を知り、見たものだけ確認済みにする | 手動 |
| [SCT-GUI-003](#sct-gui-003) | 差分収集を中断せず、届いた通知から未読一覧を開く | 手動 |
| [SCT-SMB-001](#sct-smb-001) | 共有先の一時切断をファイル削除と取り違えず、復旧後に更新を知る | 手動・専用SMB環境 |

「自動」は `test\run_sct.bat` の対象。「手動」は仕様のみで、同バッチでは実行・集計しない。各実行の合否はこの表ではなく試験記録に残す。

## 共通条件と記録

- 配布物は空の書き込み可能なローカルフォルダに展開し、ケースごとに検証データを初期化する。通常利用の設定・DB・監視先は使わない。GUI試験は対話操作できるWindowsで、自動GUI試験の共通前処理が同じセッションの起動済みアプリを通常終了し、GUI専用の展開先で初期状態を作る。終了を確認できなければ `BLOCKED`。普段の設定や履歴は消さない。SMBは専用の検証共有だけを使う。
- 自動試験は `result.json` の `results[].id` と `specification` でこの仕様に対応させ、`testCode` で実行コードを確認する。`runnerRevision` は試験側のGit情報（ローカル変更の有無を含む）、`artifact.sha256` は試験したZIPの識別子。持ち込みのZIPの製品コミットを試験側のコミットとみなさない。`SCT-SETUP` は配布物の用意に失敗したときの実行記録であり、ユースケースのIDではない。
- 手動試験にはケースID、日時、配布ZIP名とSHA-256、OSと必要な環境情報、実測結果と証跡を記録する。結果は `PASS`（期待結果をすべて確認）、`FAIL`（不一致）、`BLOCKED`（前提を満たせず判定不能）、未実施を区別する。画面の証跡は検証用データのみを含める。

## SCT-CLI-001

自動試験仕様の正本は [Checkpoint.feature](Features/Checkpoint.feature)。各手順の実装は [CheckpointSteps.cs](Steps/CheckpointSteps.cs)。結果は `result.json`、手順単位の証跡は `cucumber.ndjson`、テスト結果は `sct.trx` に出る。

## SCT-GUI-001

**目的:** メイン画面のメニューを経由せずに収集を始める。

**前提:** 展開した `かわったよ.exe`。共通前処理で通常版の終了とGUI専用の初期状態を確認できるWindowsセッション。

| 手順 | 期待結果 |
|---|---|
| `かわったよ.exe --show-collector` を実行する | 試験で起動したプロセスが終了せず、15秒以内にタイトルに「差分収集」を含むウィンドウが現れる |

ここでは起動のみを確認する。画面内の操作や外部ランチャーへの登録は合格範囲に含めない。

## SCT-GUI-002

**目的:** フォルダ内の更新を一覧で見つけ、対象の更新だけを確認済みにする。

**前提:** 空の検証フォルダを2つ用意し、片方にはサブフォルダを作る。両方を再帰監視に登録し、初回照会を完了させる。

| 手順 | 期待結果 |
|---|---|
| 各監視先にテストファイルを1つずつ追加し、次の照会を待つ | 未読一覧に両方の監視先が出る。フォルダは既定で折りたたまれ、展開すると更新されたファイルを確認できる |
| 片方の監視先の親行を右クリックし「確認済みにする」を選ぶ | その監視先の未読が消え、もう片方の未読は残る。実ファイルはどちらも残る |
| アプリを完全終了し、同じ展開先から再起動する | 確認済みにした変更は未読に戻らず、未確認の変更は残る |

## SCT-GUI-003

**目的:** 差分収集を開いたまま、Windows通知から更新内容を確認する。

**前提:** Windowsとアプリで通知を有効にする。テスト用フォルダを監視登録し、初回照会を完了させる。通知の安定待ち時間は試験記録に残す。

| 手順 | 期待結果 |
|---|---|
| 「ツール」から「差分収集」を開く | 更新監視とは別のウィンドウが開く |
| 監視フォルダにファイルを追加し、照会と安定待ちを経て届いた通知をクリックする | 更新監視画面が前面に出て未読項目を確認できる。差分収集ウィンドウは閉じたり最小化されたりせず、引き続き操作できる |

未読に出ることと、Windows側のバナーが出ることは別々に記録する。通知がOS設定などで受信できずクリックを試せない場合、その操作は合格にしない。

## SCT-SMB-001

**目的:** 共有フォルダに一時的につながらないとき、ファイルが消えたと誤認しない。

**前提:** 監視PC Aと更新PC Bが同じ専用の検証共有を使用。AはUNCパスで監視登録し、初回照会を完了させる。テスト用の既存ファイルを1件置く。Aだけの検証共有へのアクセスを安全に遮断・復旧できること。

| 手順 | 期待結果 |
|---|---|
| Aから検証共有へのアクセスを遮断し、照会を待つ | Aに照会失敗が表示される。既存のファイルが削除されたという未読・履歴は作られない |
| 遮断中にBで既存ファイルを内容とサイズが変わるように更新する | Bからは共有にアクセスでき、更新後のファイルを読み直せる |
| Aのアクセスを復旧し、正常な照会を待つ | 照会が正常に戻り、更新を検知する。同じ変更を繰り返し登録せず、誤った削除も残らない |

## 仕様を追加するとき

目的、前提、操作ごとの期待結果、実施方法、必要な証跡を書く。欠けるとデータ保護に影響する操作では、元ファイル・既存出力・未読など「何が変わってはいけないか」も明記する。新機能や不具合修正で利用者から見える振る舞いが変わる場合は、同じ変更で該当ケースを追加・更新する。既存ケースはIDを維持し、自動化した場合だけ一覧の実施方法を変更する。
